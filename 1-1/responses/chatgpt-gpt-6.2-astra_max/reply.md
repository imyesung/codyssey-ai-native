## 3. 위에서부터 따라갈 작업 순서

표의 ‘비교’, ‘설계’, ‘로그’, ‘미해결’은 위 네 문서를 가리킨다. 중괄호가 있는 문구는 **복사용 작성 예시**다. 중괄호를 실제 값으로 바꾼 뒤 사용한다. 실습은 브라우저에서 진행하며, 처음부터 개인정보와 사내 기밀을 제외한 자료를 고른다. 원문 §6, §7에 따른다.

### 과업과 모델을 정한다

| 행동 | 직접 입력할 값 또는 AI에 복사할 문구 | 결과를 넣을 파일과 항목 | 다음에 가져갈 값 |
|---|---|---|---|
| 1. 반복 과업 하나를 정의한다. | 누가 어떤 문제를 겪는지, 무엇을 넣어 어떤 형식으로 받을지 쓴다. 기존 정의가 있으면 참고한다. | 설계 / 과업 정의 | 과업, 사용자, 입력 자료, 출력 규격 |
| 2. 수행한 작업 한 건을 기록한다. | 직접 한 일의 대상과 방법을 한 줄로 쓴다. 이후 작업 중에도 반복한다. | 로그 / 작업 기록 | 마지막으로 한 일 또는 막힌 지점 |
| 3. 대화 전 검증 전략을 정한다. | 어떤 답을 사실 오류로 의심하고 무슨 자료에서 확인할지 정한다. | 설계 / 검증 전략 | 의심할 조건과 확인 자료 |
| 4. 검증 질문을 5개 이상 준비한다. | 초안이 필요하면 `다음 자료에서 내가 정답을 확인할 수 있는 사실 질문 5개를 제안해 줘. 질문만 써 줘. 자료: {자료}`. 정답과 근거 위치는 직접 확인한다. | 설계 / 환각 검증 표의 앞 두 열 | 본 대화에서 물을 질문 원문 |
| 5. 비교할 모델을 3종 이상 고른다. | 접근 가능한 모델 가운데 무료 요금제로 쓸 수 있는 모델을 하나 이상 포함한다. | 비교 / 비교표 머리, 무료 요금제 항목 | 모델 목록 |
| 6. 비교 기준을 4개 이상 정한다. | 각 기준에서 무엇을 확인하고 어느 쪽에 높은 점수를 줄지 정한다. | 비교 / 비교 기준, 점수 척도 | 공통 채점 기준 |
| 7. 공통 프롬프트를 완성한다. | `다음 자료로 {과업}을 수행해 줘. 읽을 사람은 {사용자}다. 출력 규격은 {규격}이다. 입력 자료: {자료 전문}` | 비교 / 공통 프롬프트와 입력 | 모델마다 똑같이 보낼 전문 |
| 8. 각 모델에서 공통 프롬프트를 실행한다. | 7번 전문을 그대로 보낸다. 실행 당시의 모델명, 버전, 시점과 응답을 확보한다. | 비교 / 모델별 응답, 비교표 머리 | 모델별 실제 출력 |
| 9. 각 출력을 채점한다. | 기준마다 모델별 점수와 각 점수의 근거를 적는다. | 비교 / 비교표 | 근거가 채워진 표 |
| 10. 본 대화에 쓸 모델을 선정한다. | 어느 기준을 중요하게 보았으며 그 결과가 선택에 어떻게 작용했는지 직접 쓴다. | 비교 / 최종 선정 | 선정 모델 |

|---|---|---|---|
| 11. 페르소나를 정한다. | `이 업무를 맡을 페르소나의 이름, 역할, 전문 분야, 말투, 금지 사항, 우선순위를 각각 한 줄로 써 줘. 업무: {과업 정의}` | 설계 / 페르소나 | 확정한 여섯 항목 |
| 12. 시스템의 업무 지침을 작성한다. | `다음 페르소나와 출력 규격으로 시스템 지침 본문을 써 줘. 과업 예시는 아직 넣지 마. 페르소나: {여섯 항목}. 규격: {규격}. 단계적 추론 유도 사용 여부: {내 선택}` | 설계 / v1의 업무 지침, 단계적 추론 유도 추가 여부 | 예시 없는 지침 |

| 14. 실제 유저 프롬프트를 만든다. | 13번 틀을 복사해 이번 실행의 값으로 채운다. | 설계 / 유저 프롬프트 | 두 기법에 공통으로 쓸 입력 전문 |
| 15. Few-shot 예시를 3건 이상 완성한다. | `이 지침에 넣을 사용자 입력과 기대 응답의 짝을 3건 만들어 줘. 한 건에서는 필수 정보가 빠진 요청에 AI가 확인 질문을 먼저 하게 해 줘. 지침과 자료: {지침, 자료}` | 설계 / v1 안의 Few-shot 예시 | 지침과 예시가 모두 든 v1 전문 |
| 16. 선정 모델에서 Zero-shot을 실행한다. | 12번 지침만 적용하고 14번 유저 프롬프트를 보낸다. | 설계 / Zero-shot 결과 | 첫 번째 실제 출력 |
| 17. 본 대화에 v1을 적용한다. | 새 대화의 지침 입력란 또는 첫 메시지에 v1 전문을 넣는다. 첫 메시지 방식을 택하면 그 발화부터 로그에 담는다. | 로그 / 실행 정보와 대화 전문 | Few-shot 예시가 적용된 대화 |
| 18. Few-shot을 실행한다. | 14번 유저 프롬프트를 그대로 보낸다. 이 대화를 10턴 실습으로 이어 간다. | 설계 / Few-shot 결과, 로그 / 대화 전문 | 두 번째 실제 출력 |
| 19. 두 출력의 차이를 적는다. | 같은 입력에서 무엇이 달라졌고 무엇이 같았는지 실제 응답에 대조해 쓴다. | 설계 / 두 결과에서 확인한 차이 | 예시 적용 전후의 관찰 |

Few-shot 적용은 필수다. 단계적 추론 유도는 선택할 수 있고 **추가 여부의 기록은 필수**다. 두 기법의 차이를 살피기 위해 이 순서표에서는 모델, 업무 지침, 유저 입력을 맞추었다. 원문 §4.3, §4.4, §4.5, §6에 해당한다.

| 33. 각 과업에서 시도한 프롬프트를 옮긴다. | 해당 시도에 실제로 보낸 원문을 복사한다. | 미해결 / 시도한 프롬프트 원문 | 시도한 방법 |
| 34. 과업마다 막힌 이유를 직접 쓴다. | 정확한 원인을 모르면 무엇을 해 보았고 어디서 멈췄는지 쓴다. | 미해결 / 막힌 이유 | 제출할 미해결 기록 |

**25번 판정 기준.** A는 정답을 맞히고 근거도 제시한 경우다. B는 모를 때 ‘모른다’ 또는 ‘확인 필요’를 밝히고 확인 절차까지 제안한 경우다. 둘 중 하나만 충족해도 Pass이고 둘 다 충족하지 못하면 Fail이다. 정답에 근거가 빠져 Fail이 된 경우, 환각 표시를 하려면 사실과 다른 내용도 실제로 확인되어야 한다. 환각과 문맥 끊김이 모두 없으면 그 사실을 기록할 수 있다. 원문 §4.5~§4.9, §7에 해당한다.

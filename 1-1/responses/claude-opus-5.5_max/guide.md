# AI Native 1-1 시작 키트: 제출 트리, 빈 양식, 작업 순서표

Nov 19, 2026 · @seo

## 읽는 법

이 문서는 미션 원문 한 편만으로 만든 제출 준비물이다. 1절 트리로 폴더를 만들고, 2절 양식을 파일에 붙이고, 3절 순서표를 위에서부터 따라간 뒤, 4절로 제출 전에 대조한다.

괄호 속 '원문 4-5'는 원문 '4. 기능 요구 사항'의 5번이다. 같은 식으로 원문 2-1은 '2. 최종 결과물'의 산출물 1, 원문 5-3은 보너스 과제 3이고, '원문 2 끝'은 산출물 4 다음의 제출 문단이다. 원문 6, 7, 8은 개발 환경, 제약 사항, 결과 예시다.

이름 표시는 두 가지다. `[예시]`는 원문이 '참고할 수 있다'고 든 구조의 이름이라 바꿔도 되고, `[직접]`은 원문에 없어 직접 정하는 이름이다. 원문이 이름을 고정한 파일은 없다.

'미지정'은 원문이 정하지 않은 것이다. 보충한 조건에는 근거를 붙였다. '문언'은 원문 문장에서, '목적'은 원문 7이 밝힌 이유에서 끌어낸 것이고, '추론'은 원문 근거 없이 권하는 방법이다.

양식의 빈칸은 직접 실행하거나 판정해서 채운다. '(직접 작성)'이 붙은 칸은 원문 7에 따라 AI에게 맡기지 않는다. 양식 속 `<!-- -->` 주석은 GitHub 화면에 보이지 않으므로 남겨도 되고 지워도 된다.

## 1. 제출 폴더와 파일 트리

원문이 고정한 것은 파일 이름이 아니라 네 문서, 한 폴더, Markdown 또는 PDF, GitHub 저장소, 저장소 URL 제출이다(원문 2 끝). 원문이 정한 이름은 문서 이름 넷뿐이고, 트리의 파일 이름은 원문의 예시 구조를 따랐다.

```text
.                                [직접] 저장소. 이름 미지정, 이 저장소의 URL을 제출
|-- docs/                        [예시] 네 문서를 모으는 '한 폴더'
|   |-- model-comparison.md      [예시] 산출물 1 비교 보고서 (원문 2-1)
|   |-- system-design.md         [예시] 산출물 2 설계 문서 (원문 2-2)
|   |-- run-log.md               [예시] 산출물 3 실행 로그 (원문 2-3)
|   `-- unresolved.md            [예시] 산출물 4 미해결 기록 (원문 2-4)
|-- README.md                    [예시] 선택. 네 문서의 순서와 한 줄 소개 (원문 2 끝)
`-- bonus/                       [직접] 선택. 보너스를 할 때만, 위치와 이름 미지정 (원문 5)
    |-- bonus.md                 [직접] 보너스 1, 2, 3 기록
    |-- Code.gs                  [직접] 선택. 보너스 3 스크립트 사본, 키 값 제외
    `-- assets/                  [직접] 이미지. 형식 미지정 (.png 권장)
        |-- bonus1-deploy.png    [직접] 보너스 1 배포한 화면 캡처
        |-- bonus1-reuse.png     [직접] 보너스 1 다시 불러 쓴 결과 캡처
        `-- bonus2-visual.png    [직접] 보너스 2 생성한 시각 자료
```

원문이 정한 문서 이름은 'LLM 모델 비교와 선정 보고서', '시스템 설계 문서', '실행 로그', '미해결 기록'이다(원문 2). 2절 양식은 이 이름을 각 파일의 제목으로 쓴다.

네 문서는 각각 .md 대신 .pdf로 내도 된다. 그때도 대화 로그는 편집하지 않은 원문이어야 하고, API 키, 비밀번호, 계정 이메일은 적지 않는다(원문 2 끝).

새 저장소를 만들지, 기존 저장소의 하위 폴더에 넣을지는 미지정이다. 기존 미션 저장소(codyssey-ai-native)에 넣는다면 이전 미션의 1-1 폴더와 겹치지 않는 이름을 정하고, 제출 URL에 그 폴더 경로를 붙일지 확인한다. 저장소 공개 여부도 원문에 없으니 검토자가 열 수 있는지 제출 전에 확인한다.

bonus/를 docs/ 밖에 둔 것은 네 문서만 모인 폴더를 분명히 하려는 추론이다. 원문 6은 브라우저 도구만으로 수행하라고 하므로, GitHub 웹 화면의 Add file 메뉴로 파일을 만들고 이미지를 올리면 된다.

## 3. 작업 순서표

아래 표를 위에서부터 한 행씩 따라가면 네 문서가 채워진다. 담당 열이 판단, 직접 작성, AI Pn인 행은 3-1에서 같은 순서 번호를 찾아 입력할 것이나 복사할 프롬프트를 본다.

담당 열은 다섯 가지다. 판단은 내가 정해 입력하는 칸이고, 직접 작성은 원문 7이 AI에게 맡기지 말라고 한 판단이다. 실행은 화면에서 하는 일, 복사만은 생성 결과를 AI를 거치지 않고 그대로 옮기는 일, AI Pn은 3-1의 프롬프트를 별도 창에 붙이는 일이다.

### 3-1. 판단 입력과 AI 프롬프트

표에서 담당이 판단, 직접 작성, AI Pn인 행만 순서 번호대로 모았다. 프롬프트는 선정 모델과 대화하는 창이 아닌 별도 창에 붙여 실행 로그와 섞이지 않게 한다(추론). 프롬프트 속 `<<...>>`는 보내기 전에 내 값으로 바꾸는 자리이고, `{...}`는 결과물에 남길 빈칸이다.

#### A1 판단: 저장소와 미션 폴더

새 저장소인지 기존 저장소의 하위 폴더인지, 그 이름과 공개 여부를 정한다. 원문은 저장소 URL 제출만 정했다(원문 2 끝). 기존 미션 저장소에 넣는다면 이전 미션의 1-1 폴더와 이름이 겹치지 않게 한다.

#### B1 판단: 반복 과업

자기 업무에서 반복되는 과업을 한 문장으로 적는다(원문 4-1). 이미 정의한 과업이 있으면 그것을 참고한다. 고를 때 세 가지를 본다.

1. 개인정보와 사내 기밀을 빼고도 입력 자료를 만들 수 있는가(원문 7).
2. 입력 자료에 날짜, 숫자, 이름처럼 정답을 대조할 사실이 있는가. 검증 질문 5개의 재료가 된다(원문 4-6).
3. 조건이 여러 개 얽힌 세부 작업이 있는가. 너무 단순하면 미해결 2건을 채우기 어렵다(원문 4-9, 추론).

#### B2 판단: 세부 정의 (P1 선택)

타겟 사용자(결과를 받아 쓰는 사람), 입력 데이터 형태(무엇을 어떤 형식과 분량으로 넣는가), 출력 규격(분량, 항목, 형식)을 적는다. 출력 규격은 셈 수 있게 쓴다. C2의 비교 기준과 E7의 판정이 이 규격을 잣대로 삼는다.

P1은 메모를 네 줄로 정리하며 빠진 곳과 모호한 곳을 짚게 하는 점검용이다.

```text
아래는 LLM에 맡기려는 반복 업무 과업 메모다. 다음 네 줄로만 정리해 줘.
과업(한 문장) / 타겟 사용자 / 입력 데이터 형태 / 출력 규격

규칙
1) 메모에 없는 내용은 보태지 않는다. 빠진 항목은 "미정"으로 둔다.
2) 출력 규격이 분량, 항목, 형식으로 셈 수 있게 적혀 있지 않으면 모호한 곳을 한 줄로 짚는다.
3) 개인정보나 회사 기밀로 보이는 표현이 있으면 그 위치를 짚는다.
4) 입력 자료에 정답을 대조할 날짜, 숫자, 이름이 들어가는지 한 줄로 답한다.

[메모]
<<과업 메모>>
```

#### B3 판단: 업무 문제

타겟 사용자가 이 과업에서 겪는 문제를 한두 문장으로 쓴다. 무엇이 반복되고, 어디서 시간이 들거나 틀리는지를 담는다(원문 2-2, 4-3).

#### C1 판단: 모델 3종

모델 A, B, C의 이름, 버전, 요금제를 적는다. 1종 이상은 무료 요금제로 쓸 수 있어야 한다(원문 4-2, 6). 화면에 버전 표기가 없으면 보이는 이름 그대로 적고 '버전 표기 없음'을 덧붙인다(추론).

#### C2 판단: 비교 기준과 척도

기준 4개 이상과 점수 척도를 적는다. 기준은 출력 규격과 업무 문제에서 끌어오고, 근거 칸에 셈 수 있는 사실을 적을 수 있게 정한다. 예시(원문 8)는 형식 준수, 결정 사항 누락, 사실 오류, 지시 재확인과 1에서 5 척도다.

출력을 보기 전에 정해 두고, 바꾸면 작업 기록에 이유를 남긴다(추론).

#### C3 AI P2: 비교용 과업 프롬프트

받은 뒤 출력 규격 밖의 조건이 붙지 않았는지 본다.

```text
같은 과업을 LLM 세 개에 똑같이 넣어 결과를 비교하려고 한다. 비교용 과업 프롬프트 한 개를 써 줘.

규칙
1) 역할 부여, 예시, 단계적 추론 지시는 넣지 않는다. 과업 지시와 출력 규격만 담는다.
2) 출력 규격은 아래 문장을 그대로 옮기고 새 조건을 보태지 않는다.
3) 입력 자료가 들어갈 자리는 {입력 자료}로 비워 둔다.
4) 프롬프트 본문만 출력한다.

과업: <<과업 문장>>
입력 데이터 형태: <<입력 데이터 형태>>
출력 규격: <<출력 규격>>
```

#### C6 판단: 점수와 근거

기준마다 모델별 점수와 근거를 적는다. 근거 칸에는 관찰한 사실을 쓴다(예시, 원문 8: 'A 1건, B 0건, C 2건 누락'). 점수가 선정 근거가 되므로 직접 매긴다(원문 7, 추론).

#### C7 직접 작성: 선정 결론

선정 모델 이름과 선정 근거 문장을 쓴다(원문 2-1). 어떤 약점은 프롬프트로 고칠 수 있고 어떤 약점은 고치기 어려운지 따지면 예시(원문 8)와 같은 논리가 된다. AI에게 맡기지 않는다(원문 7).

#### D1 판단: 페르소나

이름, 역할, 전문 분야, 말투, 금지 사항, 우선순위를 적는다(원문 4-3). 금지 사항에는 이 과업에서 가장 위험한 실수를, 우선순위에는 두 규칙이 부딪칠 때 무엇이 앞서는지를 쓴다. 예시(원문 8): '누락 없음이 형식보다 앞선다'.

#### D2 AI P3: 시스템 프롬프트 본문

규칙 2부터 5까지는 원문 4-6의 Pass 기준 A, B에 맞춘 것이다(추론). 과업에 맞지 않으면 빼거나 바꾼다.

```text
아래 과업 정의, 업무 문제, 페르소나로 LLM 시스템 프롬프트 본문을 써 줘.

규칙
1) 페르소나의 이름, 역할, 전문 분야, 말투, 금지 사항, 우선순위를 모두 반영한다.
2) 입력 자료에 없는 날짜, 숫자, 이름을 만들지 말라는 규칙을 넣는다.
3) 사실을 답할 때 입력 자료의 해당 부분을 근거로 짚게 한다.
4) 확인할 수 없으면 "확인 필요"라고 밝히고 확인 방법을 제안하게 한다.
5) 입력이 모호하면 추측하지 말고 먼저 되묻게 한다.
6) Few-shot 예시는 넣지 않는다. 맨 끝에 "[예시 자리]" 한 줄만 둔다.
7) 시스템 프롬프트 본문만 출력한다.

[과업 정의]
<<system-design.md 1절>>

[업무 문제]
<<system-design.md 2절>>

[페르소나]
<<system-design.md 3절>>
```

#### D3 AI P4: Few-shot 예시

대화에 쓸 S1이 아니라 S2, S3를 넣는다. 예시와 대화가 같은 자료면 검증 질문이 예시를 되풀이하는지만 보게 된다(추론).

```text
아래 시스템 프롬프트의 "[예시 자리]"에 넣을 Few-shot 예시 3개를 만들어 줘.

규칙
1) 예시 1과 예시 2는 [입력]과 [출력] 한 쌍씩이다. 출력은 출력 규격을 정확히 지킨다.
2) 예시 3은 정보가 빠진 모호한 입력이다. [입력], [되묻는 질문], [보충 입력], [출력] 순서로 쓴다.
3) 샘플 자료에 없는 사실은 쓰지 않는다.
4) "[예시 자리]"를 바꿔 넣을 수 있게 예시만 출력한다.

[출력 규격]
<<출력 규격>>

[시스템 프롬프트]
<<P3으로 받은 본문>>

[샘플 자료]
<<S2, S3>>
```

#### D4 판단: 예시 확인

예시 출력을 S2, S3와 한 줄씩 대조해 고친다. 예시 3이 '모호한 입력, 되묻는 질문, 보충 입력, 출력' 흐름인지 본다(원문 4-4). 예시에 틀린 사실이 남으면 모델이 그것을 따라 할 수 있다(추론).

#### D7 직접 작성: Zero-shot과 Few-shot 비교

형식, 누락, 사실, 되묻기 가운데 무엇이 달라졌는지 적고, 단계적 추론 유도를 더할지와 그 이유를 쓴다(원문 4-4). 더한다면 출력 규격 밖의 풀이가 붙지 않는지 함께 본다(추론). 여기서 확정한 판을 대화에 쓰고 11절 v1로 삼는다(추론).

#### D8 AI P5: 입력 템플릿

```text
아래 과업을 반복할 때마다 그대로 복사해 쓸 입력 템플릿을 만들어 줘.

규칙
1) 매번 바뀌는 값은 {중괄호} 빈칸으로 두고, 빈칸 이름만 보고 무엇을 넣을지 알 수 있게 짓는다.
2) 출력 규격 줄을 넣는다.
3) 시스템 프롬프트에 이미 있는 규칙은 되풀이하지 않는다.
4) 템플릿 본문만 출력한다.

과업: <<과업 문장>>
입력 데이터 형태: <<입력 데이터 형태>>
출력 규격: <<출력 규격>>

[시스템 프롬프트]
<<D7에서 확정한 시스템 프롬프트>>
```

#### D10 판단: 검증 전략

사실 오류로 의심할 대답의 종류와 대조 방법을 쓴다(원문 4-6). 예를 들어 자료에 없는 날짜, 숫자, 이름, 인용과 자료와 다른 계산은 의심하고, 입력 자료의 해당 줄과 대조한다. 대화 전에 쓰고, 작업 기록에서도 이 항목이 대화 시작보다 앞에 오게 남긴다.

#### D11 판단: 검증 질문 (P6 선택)

질문 5개 이상과 정답, 정답이 적힌 자료 위치를 적는다. 자료에 정답이 있는 질문은 기준 A를, 정답이 없는 질문은 기준 B를 시험하므로 두 종류를 섞는 것을 권한다(추론). P6으로 후보를 받아도 정답은 S1과 직접 대조해 확정한다.

```text
아래 자료를 입력으로 받은 LLM의 환각을 검사할 질문 후보 8개를 만들어 줘.

규칙
1) 5개는 자료에 정답이 적힌 질문이다(날짜, 숫자, 이름, 순서). 질문마다 정답과, 정답이 적힌 자료 속 문장을 그대로 인용한다.
2) 3개는 자료에 정답이 없는 질문이다. 자료에 없다는 것을 확인할 수 있게 가장 가까운 내용의 문장을 인용한다.
3) 자료에 없는 사실을 정답으로 만들지 않는다.
4) 번호 목록으로만 출력한다.

[자료]
<<S1>>
```

#### D12 판단: 메시지 순서

보낼 메시지 순서를 정한다. 아래는 원문 4-5의 조건을 한 대화에 담는 한 가지 순서다(추론).

1. `[01]` 첫 유저 프롬프트(system-design.md 8절)
2. `[03]` 조건 변경 또는 추가 정보. 예: 출력 분량이나 대상 독자를 바꾼다.
3. `[05]` 바뀜 조건으로 다시 작성해 달라는 요청(반복 1회차)
4. `[07]` `[05]`와 글자까지 같은 메시지(반복 2회차)
5. `[09]`부터 검증 질문을 한 턴에 하나씩

AI 응답까지 세면 18턴 이상이다. `[05]` 이후 응답이 `[03]`의 조건을 지키는지가 문맥 끊김을 판정할 자리다(원문 4-7). 대화 중에는 응답을 다시 생성하거나 보낸 메시지를 고치지 않는다(원문 7, 목적).

#### E7 직접 작성: Pass 또는 Fail

질문마다 Pass 또는 Fail, 충족한 기준(A, B, 없음), 답변 턴 번호를 적는다. 정답을 맞혀도 근거가 없으면 기준 A가 아니고, '모른다'고만 하고 확인 절차를 제안하지 않으면 기준 B가 아니므로 Fail이다(원문 4-6, 문언). AI에게 판정을 맡기지 않는다(원문 7).

#### E8 판단: 지점 표시

환각 지점은 Fail로 판정한 답변과 그 밖에 사실과 다른 대답이다. 문맥 끊김 지점은 앞에서 준 조건을 뒤 턴에서 지키지 못한 응답이다(원문 4-7). 둘 다 없으면 run-log.md 6절에 나타나지 않았다고 적는다.

#### E9 판단: 반복 결과

반복한 응답이 같았는지, 달랐다면 어느 부분이 달랐는지 적는다(원문 4-5).

#### F1 직접 작성: v2 수정 방향

겨냥한 지점(턴 번호와 무엇이 어긋났는지), 고칠 내용, 고칠 이유를 쓴다. E8에서 표시한 지점이 없으면 지시와 가장 어긋난 응답 하나를 고른다(원문 4-8). 이유는 직접 쓰고(원문 7), P7에는 지점과 고칠 내용만 넘긴다.

#### F2 AI P7: 프롬프트 v2

```text
아래 프롬프트 v1을 고쳐 v2를 만들어 줘. 고칠 지점과 내용은 내가 정했으니 그 범위만 고치고 다른 문장은 그대로 둔다.

규칙
1) v2 전문을 먼저 출력한다. 바꾼 곳에 표시를 달지 않는다.
2) 그 아래에 v1과 달라진 줄만 "삭제:"와 "추가:"로 나열한다.
3) 고친 이유는 쓰지 않는다.

[고칠 지점]
<<run-log.md의 턴 번호와 무엇이 어긋났는지>>

[고칠 내용]
<<system-design.md 13절에 쓴 고친 내용>>

[v1]
<<v1 전문>>
```

#### F4 판단: 카테고리

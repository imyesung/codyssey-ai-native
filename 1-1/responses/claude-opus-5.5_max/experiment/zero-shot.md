원문의 조건을 하나씩 대조한 뒤 제출 트리, 빈 양식, 작업 순서를 정리하겠습니다.

## 요지

1) 원문이 파일 이름까지 정해 둔 파일은 없습니다. §2의 폴더 구조는 "참고할 수 있다"며 든 예시입니다.
2) 원문이 정해 둔 것은 네 문서를 한 폴더에 모아 GitHub 저장소에 올리고 저장소 URL을 제출하는 것, 그리고 형식을 Markdown 또는 PDF로 하는 것입니다(§2).
3) 원문이 선택으로 둔 것은 README.md(§2)와 보너스 과제 세 개(§5)입니다.
4) 해석이 갈리는 곳과 미지정 사항은 3-3 끝에 모았습니다.

근거 표기는 이렇게 읽으면 됩니다.

- §2-1은 "2. 최종 결과물"의 산출물 1, §4-6은 "4. 기능 요구 사항"의 6번, §5-3은 "5. 보너스 과제"의 3번입니다. §4 머리말은 4절의 첫 두 문장입니다.
- §7은 원문에 번호가 없어 위에서부터 셌습니다. §7-1 모델, 버전, 실행 시점 기록 / §7-2 로그 무편집 / §7-3 개인정보와 사내 기밀 제외 / §7-4 키와 인증 정보 제외 / §7-5 보너스 3은 절차만 기록 / §7-6 AI 활용 허용 / §7-7 이유는 직접 작성 / §7-8 판정은 직접.
- 양식 안의 위치는 "파일 이름 + 양식 절 번호"로 적었습니다. 예: system-design 9.

### 3-1. 판단 지점 (D)

- D1 (03) 과업 정의: 반복 과업 한 문장, 타겟 사용자, 업무 문제 한 문장, 입력 데이터 형태, 출력 규격을 씁니다. 이미 정의해 둔 과업이 있으면 가져옵니다(§4-1). 개인정보와 사내 기밀이 없는 과업으로 정합니다(§7-3). 출력 규격은 분량, 형식, 포함 항목처럼 확인할 수 있게 씁니다. 비교 기준과 검증 질문이 여기서 나옵니다.
- D2 (04) 입력 자료: 과업에 실제로 넣을 자료 한 건입니다. 실명, 연락처, 내부 수치는 지우거나 가상으로 바꿉니다(§7-3). 날짜와 숫자가 들어 있는 자료면 검증 질문을 만들기 쉽습니다(§4-6 괄호).
- D3 (06) 모델 3종: 모델마다 이름, 버전, 무료 요금제로 쓸 수 있는지를 적습니다. 접근할 수 있는 모델로 고르고, 1종 이상은 무료여야 합니다(§4-2, §6). 화면에 버전이 안 보이면 표시된 이름과 확인한 위치를 적습니다(미지정). 커스텀 인스트럭션이나 메모리 같은 개인화 설정이 켜져 있으면 끄거나, 켜 둔 사실을 적습니다(미지정이지만, 비교 조건을 같게 하려면 권장).
- D4 (07) 비교 기준: 기준 4개 이상과 점수 척도입니다. 출력 규격에서 뽑은 기준이면 근거를 세기 쉽습니다. §8의 형식 준수, 결정 사항 누락, 사실 오류, 지시 재확인은 예시일 뿐입니다. 결과를 본 뒤 기준을 고쳤다면 작업 기록에 남깁니다.
- D5 (12) 점수와 근거: 기준마다 모델별 점수를 매기고, 근거 칸에 모델별 관찰 사실을 적습니다. 근거는 결과 원문에서 다시 확인할 수 있는 사실(줄 수, 누락 건수 등)로 씁니다. P2 관찰표에 나온 숫자는 원문을 보고 다시 셉니다.
- D6 (13) 선정 근거: 선정 모델 하나와 근거 문장입니다. 직접 씁니다(§7-7). 점수 합계 말고도, 그 약점을 프롬프트로 고칠 수 있는지를 따져 볼 수 있습니다. §8 예시의 선정 근거가 이 논리입니다.
- D7 (14) 페르소나: 이름, 역할, 전문 분야, 말투, 금지 사항, 우선순위입니다(§4-3). 금지 사항을 이 과업에서 실제로 걱정되는 오류에 맞추면 뒤의 검증, 개선 단계와 이어집니다.
- D8 (17) 예시 검토: 출력이 출력 규격을 지키는지, 예시 3의 입력이 정말 모호한지, 예시 안에 사실 오류가 없는지 봅니다. {입력 자료}가 예시에 섞이면 21의 비교가 흐려집니다. 예시를 넣을 위치는 미지정입니다. 다만 보너스 1에서 시스템 프롬프트를 그대로 배포하므로, 시스템 프롬프트에 넣어 두면 재사용이 쉽습니다.
- D9 (18) 입력 템플릿: 바뀌는 부분을 {중괄호}로 둔 양식입니다. 다른 자료를 넣어도 고칠 곳 없이 그대로 쓸 수 있어야 합니다(§4-4).
- D10 (22) 두 결과의 차이: 형식, 누락, 되묻기 여부 등에서 무엇이 달라졌는지 적습니다. 20과 21은 같은 모델, 같은 입력으로 돌리고 예시 유무만 다르게 하기를 권장합니다(원문은 미지정). 08~10의 결과를 Zero-shot 결과로 다시 써도 되는지는 미지정입니다. 그렇게 하면 예시 유무뿐 아니라 페르소나 유무까지 함께 달라집니다.
- D11 (23) 단계적 추론 유도: 넣을지 말지와 그 이유입니다. 넣었다면 어느 단계에 왜 넣었는지 적습니다(§3). 넣기로 했다면 24에 반영합니다.
- D12 (25) 검증 전략: 사실 오류로 의심할 대답의 유형과 확인 방법입니다. 대화를 시작하기 전에 씁니다(§4-6). 예시(제안): 입력 자료의 날짜, 숫자, 이름을 다시 말하는 대답, 자료에 없는 내용을 단정하는 대답.
- D13 (27) 검증 질문: 질문 5개 이상과, 질문마다 정답과 출처를 적습니다. 내가 정답을 확인할 수 있는 질문이어야 합니다(§4-6). 자료에 없는 것을 묻는 질문을 하나 넣으면 기준 B를 시험할 수 있습니다(제안). 정답은 P5의 답을 옮기지 말고 자료에서 직접 찾습니다.
- D14 (32) 반복 비교: 같은지 다른지, 다르다면 어느 부분인지 적습니다. "같다"의 기준(글자 단위인지 내용 단위인지)은 미지정이므로, 무엇을 기준으로 봤는지 함께 적습니다. "두 차례 이상 반복"이 총 2회인지, 첫 입력 뒤 2회 더인지는 원문만으로 확정되지 않습니다. 총 3회 보내면 두 해석을 모두 충족합니다. 반복은 조건을 바꾸기 전에 합니다. 조건을 바꾼 뒤에 반복하면 차이가 조건 때문인지 구분할 수 없습니다. 새 대화에서 반복해도 되는지는 미지정이며, 그렇게 했다면 run-log 5에 남깁니다.
- D15 (33) 조건 변경: 출력 규격 하나를 바꾸거나 새 정보를 주는 발화입니다. 1회 이상 넣습니다(§4-5). 뒤 턴에서 지켜지는지 확인할 수 있는 조건이면 문맥 끊김 판정에도 쓸 수 있습니다(§4-7).
- D16 (38) Pass 또는 Fail: Q마다 충족 기준(A, B, 없음)과 판정을 적습니다. 정답을 맞혀도 근거를 함께 제시하지 않았다면 A가 아닙니다. 모른다고만 하고 확인 절차를 제안하지 않았다면 B가 아닙니다. 둘 다 Fail입니다(§4-6). 판정을 AI에 맡기지 않습니다(§7-8).
- D17 (39) 환각 표시: 해당 AI 발화 다음 줄에 표시하고, 색인에 위치를 적습니다. 환각은 사실과 다른 대답입니다(§4-7). Fail이 모두 환각인 것은 아닙니다. 근거만 빠진 정답은 Fail이지만 사실과 다르지는 않습니다. 검증 질문 밖의 대답에서도 환각을 찾습니다.
- D18 (40) 문맥 끊김 표시: 몇 번째 발화에서 준 조건을 몇 번째 발화에서 놓쳤는지 적습니다. 문맥 끊김은 앞에서 알려 준 조건을 AI가 뒤 턴에서 유지하지 못한 것입니다(§4-7). 환각과 문맥 끊김이 둘 다 없었으면 색인에 "나타나지 않았다"고 적습니다(§4-7).
- D19 (41) v2 대상: 고칠 표시 번호를 1개 이상 고릅니다. 표시가 하나도 없으면 지시와 가장 어긋난 응답 하나를 정합니다(§4-8). 무엇을 v1로 둘지는 원문이 정하지 않았습니다. 그 지점을 만든 프롬프트(시스템 프롬프트나 유저 프롬프트)를 v1로 두면 수정 이유가 자연스럽게 이어집니다.
- D20 (44) 수정 이유: 겨냥한 지점, 바꾼 내용, 바꾼 이유를 적습니다. 직접 씁니다(§7-7). P6에는 이유를 쓰지 않도록 조건을 넣어 두었습니다.
- D21 (46) 카테고리: 프롬프트마다 "페르소나"나 "텍스트 생성"을 붙입니다. 역할과 말투를 지정하는 프롬프트는 페르소나, 그 밖에 글을 만들게 하는 프롬프트는 텍스트 생성입니다(§4-8). 실제로 사용한 프롬프트에만 붙이고 새로 만들지 않습니다(§4-8). v2에 라벨을 붙이려면 45에서 v2를 실제로 실행해 두는 편이 안전합니다(해석). §4-8 첫째 항목만 보면 v2 실행 자체는 요구되지 않습니다.
- D22 (47) 미해결 과업: 과업 2건 이상과 각 과업 이름입니다. 프롬프트를 고쳐도 끝내 원하는 결과가 나오지 않은 것만 고릅니다(§4-9). 사실이 틀린 결과도 여기에 해당합니다(§8). 성공한 시도는 적지 않습니다(§4-9). "고쳐도"라는 문언으로 보아, 고쳐 본 시도가 있어야 맞습니다(해석).
- D23 (49) 막힌 이유: 무엇을 시도했고 어디서 멈췄는지 적습니다. 원인을 추정했다면 덧붙입니다. 원인을 정확히 짚지 못해도 충족합니다(§4-9). 직접 씁니다(§7-7).

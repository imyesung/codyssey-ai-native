## 제출 트리

```text
.                            [직접] GitHub 저장소. 이름 미지정
├── docs/                    [예시] 폴더 이름. 네 문서를 한 폴더에 두는 것은 [원문]
│   ├── model-comparison.md  [예시] 산출물 1. 비교 보고서
│   ├── system-design.md     [예시] 산출물 2. 설계 문서
│   ├── run-log.md           [예시] 산출물 3. 실행 로그. 보너스 3 기록 [제안]
│   └── unresolved.md        [예시] 산출물 4. 미해결 기록
└── README.md                [예시][선택] 네 문서의 순서와 한 줄 소개
```

표기
- [원문]: 원문이 정한 것이다.
- [예시]: 원문의 참고 구조에 나온 이름이다. 그대로 써도 되고 바꿔도 된다.
- [직접]: 이름을 직접 정한다.
- [선택]: 내지 않아도 된다.
- [제안]: 원문에 없는 편집 방식이다.
- 절 번호: §2-1은 원문 '2. 최종 결과물'의 1번이다. §4-5는 '4. 기능 요구 사항'의 5번, §5-3은 '5. 보너스 과제'의 3번이다.

원문이 고정한 파일 이름은 없다. §2 마지막 문단은 폴더 구조를 "참고할 수 있다"고만 적었다.

원문이 정한 제출 조건
- 비교 보고서, 설계 문서, 실행 로그, 미해결 기록 네 문서를 한 폴더에 모은다(§2).
- 문서는 Markdown 또는 PDF로 쓴다(§2).
- GitHub 저장소에 올리고 저장소 URL을 제출한다(§2).
- 대화 로그에는 편집하지 않은 원문을 넣는다(§2, §7).
- API 키, 비밀번호, 계정 이메일, 인증 정보는 적지 않는다(§2, §7).

미지정
- 저장소 이름. 새 저장소를 쓸지 기존 저장소를 쓸지. 공개 범위.
- URL 제출처와 기한.
- 업로드 방법. §6은 요구사항 전체를 브라우저 도구로 수행한다고만 적었다.
- 보너스 3 기록 위치. [제안] 실행 로그 끝에 절을 하나 둔다.
- 보너스 3 코드를 파일로 낼지. 코드는 Apps Script 편집기에서 실행한다. [제안] 키를 뺀 코드를 실행 로그에 코드 블록으로 싣는다. 이렇게 하면 새 파일이 생기지 않는다.
- 보너스 1, 2는 고르지 않았다. 고르면 이미지(배포 화면, 시각 자료)가 생긴다. 그 이름과 위치도 미지정이다.

[제안] 예시 이름을 그대로 쓴다. 그러면 원문 구조와 바로 대조할 수 있다.

## 빈 양식

- 문서 제목은 원문의 산출물 이름(§2)을 따랐다.
- §8 예시에 없는 필수 항목도 넣었다. §8이 예시에 없는 증거 항목도 넣으라고 했기 때문이다.
- `<!-- -->` 주석은 GitHub 화면에 보이지 않는다. 주석에는 조건과 절 번호를 적었다.
- 대괄호와 빈 칸은 직접 채운다. 실행 결과와 판정 칸은 비워 두었다.
- 문서 안 항목 순서는 미지정이다. §8 예시에 있는 순서는 따랐고, 나머지 순서는 [제안]이다.
- [제안] PDF로 낼 때도 이 양식으로 쓴 뒤 변환한다. 변환 방법은 미지정이다.

### 39행 세부 단계

표의 한 행을 풀어 쓴 것이다. 단계 순서는 [제안]이다.

1. 34행에서 카테고리를 단 프롬프트 하나를 고른다. [제안] 빈칸 없이 그대로 보낼 수 있는 것을 고른다. 원문은 그 프롬프트를 "그대로" 쓰라고 했다(§5-3).
2. 시스템 프롬프트를 골랐다면 P6의 "사용자 메시지로"를 "시스템 지시로"로 바꾼다. 함께 보낼 사용자 메시지도 적는다.
3. 호출할 LLM API를 정한다. 원문은 API를 정하지 않았다.
4. 그 API의 키 발급 화면에서 키를 받는다. 결제 수단 등록을 요구해 받지 못하면 그 사실을 적고 40행으로 간다(§5-3).
5. Apps Script 편집기에서 새 프로젝트를 만든다.
6. P6 프롬프트를 AI에게 보내 코드와 절차를 받는다.
7. [제안] 키를 코드 밖의 스크립트 속성에 넣는다.
8. 코드를 붙여 넣고 실행한다. 권한 승인 화면이 나오면 요청하는 권한을 읽고 승인할지 직접 정한다.
9. 편집기 실행 기록에 나온 응답이나 오류를 그대로 복사한다. 오류여도 충족한다(§5-3).

### 41행 점검 목록

원문이 정한 수량
- 문서는 4개다(§2).
- 비교 모델은 3종 이상이고, 그중 무료 요금제 모델이 1종 이상이다(§2-1, §4-2, §6).
- 비교 기준은 4개 이상이고, 기준마다 모델별 점수와 근거가 있다(§2-1, §4-2).
- 페르소나 항목은 6개다(§4-3).
- Few-shot 예시는 3건 이상이고, 그중 되묻는 흐름이 1건이다(§2-2, §4-4).
- 입력 템플릿은 1개 이상이다(§2-2, §4-4).
- 환각 검증 질문은 5건 이상이고, 질문마다 Pass 또는 Fail이 있다(§2-2, §4-6).
- 대화는 10턴 이상이다. 발화 하나가 1턴이다(§2-3, §4-5).
- 조건 변경 또는 추가 정보는 1회 이상이다(§4-5).
- 같은 입력은 "두 번 이상 반복"한다. 총 3회면 두 해석을 모두 충족한다(§2-3, §4-5).
- 프롬프트는 v1과 v2 두 판이다(§2-2, §4-8).
- 카테고리를 단 프롬프트는 3건 이상이다(§2-2, §4-8).
- 미해결 과업은 2건 이상이다(§2-4, §4-9).
- 작업 기록 건수는 미지정이다(§4-5).

조건부 예외
- 기준 A, B 중 하나만 충족해도 Pass다(§4-6).
- 환각과 문맥 끊김이 모두 없으면 없다고 적어도 충족한다(§4-7).
- 표시한 지점이 없으면 v2는 지시와 가장 어긋난 응답 하나를 고친다(§4-8).
- 원인을 정확히 짚지 못해도 무엇을 시도했고 어디서 멈췄는지 적으면 미해결 기록은 충족한다(§4-9).
- 결제 수단 등록 때문에 키를 받지 못해도 그 사실을 적으면 충족한다. 호출 결과가 오류여도 충족한다(§5-3).
- Apps Script 대신 다른 도구를 썼다면 무엇을 왜 골랐는지 적는다(§5-3).

직접 해야 하는 것
- 모델을 고른 이유, 프롬프트를 수정한 이유, 어려움을 겪은 과업, Pass 또는 Fail 판정은 직접 한다(§7).
- 막힌 이유는 직접 쓴다(§4-9).

선택
- README(§2)와 보너스 1~3(§5)은 선택이다. 이번에는 보너스 3을 골랐다.
- v2 재실행은 원문의 필수 항목이 아니다.
